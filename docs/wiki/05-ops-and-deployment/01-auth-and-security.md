# ⚙️ Аутентификация, Двухфакторная защита (MFA), RBAC и Безопасность

---

## 🔐 Механика Аутентификации и Токенов

Подсистема аутентификации NMS WebUI выполнена на базе стандартных криптографических библиотек Python (`hashlib`, `hmac`, `secrets`) без привлечения тяжелых сторонних зависимостей.

### 1. Подписанные JWT-токены с JTI:
- При авторизации создается подписанный по алгоритму **HMAC-SHA256** токен access token.
- Структура токена: `Base64(Header).Base64(Payload).Base64(Signature)`.
- В Payload токена записываются поля:
  - `sub`: ID пользователя.
  - `username`: Имя пользователя.
  - `jti`: Уникальный идентификатор сессии вида `jti-<uuid>`.
  - `iat`: Время выдачи токена.
  - `exp`: Время истечения токена (настраивается параметром `session_ttl_hours`, по умолчанию 12 часов).

### 2. Двухфакторная аутентификация TOTP (RFC 6238):
- Система поддерживает 2FA через любые стандартные приложения аутентификаторы (Google Authenticator, Яндекс.Ключ, YubiKey, 2FA Live).
- **Zero-Dependency 2FA (`mfa.py`)**: Генерация случайного Base32-секрета (160 бит), вычисление 6-значного OTP-кода по алгоритму HMAC-SHA1 и нативная генерация матричного SVG QR-кода без использования графических библиотек Image/PIL.
- **Окно временного сдвига (Time Drift Window)**: При проверке кода допускается окно рассинхронизации ±30 секунд (`window=1`) для корректной работы при неточных часах клиента.
- **Принудительный режим (`force_mfa`)**: При включении этой опции администратором все пользователи при входе обязаны привязать 2FA перед получением доступ к системе.

## 🛡 Ролевая модель доступа (RBAC)

Права доступа в NMS WebUI строго разграничиваются на основе назначенных ролей.

### Предопределенные системные роли:

| Роль | ID | Описание и область доступа |
| :--- | :--- | :--- |
| **Superuser** | `1` | Полный неограниченный доступ ко всем ресурсам системы (`system.all`). Автоматически присваивается учетной записи `root`. |
| **Admin** | `2` | Административный контроль: управление пользователями, ролями, системными настройками, скачивание бэкапов и сброс сессий. |
| **Operator** | `3` | Оперативный доступ: просмотр и редактирование настроек модулей, управление устройствами, подтверждение тревог и просмотр аудита. |
| **Viewer** | `4` | Доступ только для чтения: просмотр текущего журнала аудита и статуса системы. |

### Базовые разрешения системы (Permissions):

- `system.all` — Полный доступ ко всем функциям.
- `system.admin` — Администрирование системы (бэкапы, логи, сессии).
- `users.view` / `users.manage` — Просмотр и управление пользователями.
- `roles.view` / `roles.manage` — Просмотр и управление ролями и матрицей прав.
- `settings.view` / `settings.edit` — Просмотр и изменение системных настроек.
- `modules.view` / `modules.manage` — Просмотр и переключение динамических модулей.
- `audit.view` / `audit.export` — Просмотр и экспорт журнала аудита безопасности.
- `module.<id>.<action>` — Динамические права конкретных плагинов (например, `module.tuya.view`, `module.tuya.control`).

### Иерархия прав (Implied Permissions):
В системе реализовано автоматическое расширение управляющих прав:
- Наличие права `users.manage` автоматически дает право `users.view`.
- Наличие права `roles.manage` автоматически дает право `roles.view`.
- Наличие права `settings.edit` автоматически дает право `settings.view`.
- Наличие права `modules.manage` автоматически дает право `modules.view`.

## 📱 Управление сессиями и мгновенный отзыв токенов

Для защиты от компрометации токенов в NMS WebUI реализован механизм контроля сессий:

1. **Реестр активных сессий (`active_sessions`)**:
   - Каждая авторизация фиксируется в БД с указанием `token_jti`, IP-адреса клиента, `User-Agent` браузера и метки последнего посещения `last_seen`.
2. **Точечный отзыв сессии**:
   - Администратор или сам пользователь может завершить отдельную сессию. При этом в таблице `active_sessions` устанавливается флаг `is_revoked = 1`. При следующем запросе с этим токеном бэкенд отклоняет доступ.
3. **Глобальный сброс всех сессий**:
   - При выполнении команды «Завершить все сессии» обновляется поле `token_valid_after = <timestamp>` у пользователя. Любые токены, выпущенные до этой метки времени, мгновенно становятся недействительными.

## 🔒 Дополнительные механизмы защиты (Security Hardening)

### 1. Защита от подбора паролей (Brute-Force Lockout):
- Настраиваемые параметры `max_login_attempts` (по умолчанию 5) и `lockout_duration` (по умолчанию 30 минут).
- При превышении количества неверных вводов пароля аккаунт автоматически блокируется (`locked_until`), а в журнал аудита записывается событие `auth.login_lockout`.

### 2. Белые списки IP-адресов (IP Whitelisting):
- В настройках безопасности можно задать параметр `ip_whitelist` — список разрешенных IP-адресов или подсетей в формате CIDR (например, `192.168.1.0/24, 10.0.0.15`).
- Функция `is_ip_whitelisted()` проверяет IP-адрес клиента при каждом запросе. Доступ с неавторизованных IP мгновенно блокируется с кодом `403 IP_ACCESS_DENIED`.

### 3. Требования к сложности паролей:
- Функция `validate_password_complexity()` проверяет новые пароли: длина не менее 8 символов, наличие заглавных и строчных букв, цифр и специальных символов.

### 4. Журнал Аудита Безопасности (`audit_logs`):
- Каждое критическое действие пользователя автоматически логируется функцией `log_audit_event()`:
  - Идентификатор и логин пользователя.
  - Тип действия (`auth.login_success`, `user.create`, `SYSTEM_BACKUP`, `SYSTEM_RESTORE`).
  - Ресурс и текстовые детали события.
  - IP-адрес инициатора.
- Данные журнала доступны для фильтрации и выгрузки в формате CSV/JSON.
