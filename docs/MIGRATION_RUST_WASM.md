# Архитектурное руководство спецификации NMS на Rust + WASM + Tauri

Данный документ представляет собой подробную спецификацию целевого приложения **NMS Next-Gen**, исчерпывающий разбор и обоснование стека технологий (с аргументацией выбора и анализом альтернатив).

---

## 🏛️ Часть 1. Как работает новое приложение

### 1.1. Двойной режим работы (Dual-Mode Execution)
Новое приложение представляет собой **один бинарный файл**, который адаптирует свое поведение в зависимости от окружения и аргументов командной строки:

```

                                  │   Исполняемый файл nms   │
                                  └─────────────┬────────────┘
                                                │
                       ┌────────────────────────┴────────────────────────┐
                       ▼                                                 ▼
        [Запуск с аргументом --server]                    [Запуск без аргументов / GUI]
                       │                                                 │
      ┌────────────────┴────────────────┐               ┌────────────────┴────────────────┐
      │ Headless Daemon / Docker        │               │ Tauri Desktop App               │
      │ • Без графического окна         │               │ • Инициализирует WebView окно   │
      │ • Запускает Axum HTTP/WS 24/7   │               │ • Поднимает локальный бэкенд    │
      │ • Выполняет опрос сетей по cron │               │ • Рендерит Vue 3 UI в окне      │
      └─────────────────────────────────┘               └─────────────────────────────────┘
```

### 1.2. Структура плагинов, жизненный цикл ядра и WASM-модулей

#### А. Структура и распространение плагина (`.nms-plugin`)
Плагин распространяется как **один единый пакет-архив** с расширением `.nms-plugin` (или `.zip`), который при установке распаковывается в изолированный каталог модуля `/modules/{module-id}/`:

```
/modules/ping-collector/             # Изолированный каталог модуля
├── manifest.yaml                    # Описание модуля, маршрутов и требуемых разрешений (capabilities)
├── backend.wasm                     # Серверный WASM-модуль (бизнес-логика, Wasmtime)
└── static/                          # Статические артефакты фронтенда
    ├── ui.js                        # Скомпилированный Web Component (Vue 3 defineCustomElement)
    └── assets/                      # Иконки, стили и ресурсовые файлы
```

#### Б. Жизненный цикл ядра и WASM-песочницы
1. **Инициализация Ядра (Rust Core)**:
   * Запускается асинхронный рантайм `tokio`.
   * Подключается пул соединений БД (`sqlx` с поддержкой SQLite / Postgres).
   * Инициализируется асинхронная шина событий (`tokio::sync::broadcast`).
   * Поднимается рантайм `Wasmtime` с поддержкой `async_support` и `component_model` (WASI v2 / WIT-контракты).

2. **Загрузка и Разграничение Прав (Capabilities)**:
   * Сканируются каталоги `/modules/*/`.
   * Валидируется `manifest.yaml` плагина и его требуемые права (доступ к сокетам, интервалам опроса, системным утилитам).
   * `backend.wasm` компилируется Wasmtime в нативный код (AOT/JIT) и запускается в изолированной песочнице с лимитами памяти (например, до 128 МБ RAM).
   * Для сетевого мониторинга (`ping`, `snmp`, `tcp`) песочница использует стандартизированные **WASI 0.2 Sockets** или декларированные Host-вызовы.
   * При падении плагина (Trap / Out of Memory) ядро перехватывает исключение, регистрирует ошибку в логе и перезапускает модуль **без остановки основного сервера**.

3. **Связывание (Linking) и Маршрутизация**:
   * WASM-модуль связывается с ядром через WIT-интерфейсы (`nms:core/events`, `nms:core/storage`, `nms:core/logger`).
   * Веб-сервер Axum монтирует каталог `/modules/{id}/static/` на адрес `/api/v1/modules/{id}/static/ui.js` для отдачи браузеру статики с поддержкой HTTP ETag и gzip/brotli.

### 1.4. Взаимодействие Модуль ↔ Ядро и Модуль ↔ Модуль

Из-за строгой песочницы WASM прямое обращение к памяти других процессов или ядра невозможно. Вся коммуникация строго регламентирована двумя механизмами: **Host WIT-интерфейсами** и **Шиной Событий (Event Bus)**.

```
                  ┌─────────────────────────────────────────────────────────┐
                  │                 RUST CORE (Axum / Tokio)                │
                  │                                                         │
                  │   ┌──────────────────┐          ┌───────────────────┐   │
                  │   │  WIT Host API    │          │  Event Bus        │   │
                  │   │  (Storage/Logs)  │          │  (tokio broadcast)│   │
                  │   └────────▲─────────┘          └────────▲──────────┘   │
                  └────────────┼─────────────────────────────┼──────────────┘
                               │ Host Call (WIT)             │ Pub / Sub (WIT)
            ┌──────────────────┴─────────────────────────────┴──────────────────┐
            │                     WASMTIME RUNTIME (Sandbox)                     │
            │                                                                    │
            │   ┌──────────────────────────┐    RPC    ┌──────────────────────┐  │
            │   │  Module A (Ping)         ├──────────►│  Module B (Topology) │  │
            │   │  backend.wasm            │  через    │  backend.wasm        │  │
            │   └──────────────────────────┘  Ядро     └──────────────────────┘  │
            └────────────────────────────────────────────────────────────────────┘
```

#### А. Взаимодействие Модуля с Ядром (Module ↔ Core via Host WIT API)
Ядро экспортирует в песочницу Wasmtime стандартный набор WIT-контрактов (WebAssembly Interface Types), заменяющий старый Python `ModuleContext`:

1. **`nms:core/events@1.0.0`**: Публикация событий в общую шину ядра и подписка на входящие топики.
2. **`nms:core/storage@1.0.0`**: Изолированное хранилище Key-Value и безопасное выполнение разрешенных SQL-запросов плагина.
3. **`nms:core/logger@1.0.0`**: Передача логов плагина в единую системную трассировку NMS (`tracing`).
4. **`nms:core/notify@1.0.0`**: Отправка системных алеротов и push-уведомлений пользователям.
5. **`nms:core/cron@1.0.0`**: Регистрация периодических фоновых задач.

*Пример WIT-контракта (`nms-core.wit`):*
```wit
package nms:core@1.0.0;

interface events {
    record event-message {
        topic: string,
        payload: list<u8>,
        sender-module: string,
    }
    publish: func(msg: event-message) -> result<_, string>;
    subscribe: func(topic: string) -> result<_, string>;
}

interface storage {
    get: func(key: string) -> result<option<list<u8>>, string>;
    set: func(key: string, value: list<u8>) -> result<_, string>;
}
```

#### Б. Взаимодействие Модулей МЕЖДУ собой (Module ↔ Module)
Межмодульное взаимодействие делится на два паттерна:

1. **Асинхронное взаимодействие (Pub/Sub Event Bus — Основной паттерн)**:
   * **Модуль-источник (например, `ping-collector`)**: При обнаружении недоступности узла публицирует событие через Host API: `events::publish("device:down", payload)`.
   * **Модуль-приемник (например, `telegram-notifier`)**: Подписывается при старте на топик `device:down` и автоматически получает входящие сообщения от ядра.
   * **Преимущество**: Нулевая связанность модулей (Loose Coupling). Отключение одного плагина не ломает работу остальных.

2. **Прямое связывание компонентов по WIT-интерфейсам (WASM Component Model Direct Linking & Typed Interfaces)**:
   * Вместо устаревшего классического RPC с тяжелой JSON-сериализацией, в рантайме Wasmtime применяется **нативное связывание компонентов (Component Model Dynamic Linking)**.
   * **Как это работает**: Модуль-провайдер (например, `topology-provider`) декларирует и экспортирует тип публичного WIT-интерфейса (`nms:topology/api`). Модуль-потребитель импортирует этот интерфейс.
   * Рантайм Wasmtime на лету связывает экспорты и импорты плагинов через **Canonical ABI**. Передача данных происходит напрямую в памяти с минимальными накладными расходами (Zero-Copy / Direct Call) со строгой типизацией на этапе связывания.
   * **Контроль доступа**: Ядро выступает в роли роутера/линкера компонентов и на этапе загрузки проверяет разрешенные `dependencies` в `manifest.yaml`.

*Пример WIT-интерфейса межмодульного вызова (`nms-topology.wit`):*
```wit
package nms:topology@1.0.0;

interface provider {
    record network-node {
        id: string,
        ip: string,
        status: string,
    }
    get-nodes: func() -> result<list<network-node>, string>;
}
```

## 🔬 Часть 2. Обоснование Стека Технологий (Technology Rationale & Alternatives)

Ниже приведен детальный анализ выбора каждого элемента стека с аргументацией, почему были отвергнуты альтернативные варианты.

---

### 2.1. Язык Ядра: **Rust**

* **Почему выбран Rust**:
  1. **Безопасность памяти без GC (Garbage Collector)**: Отсутствие пауз сборщика мусора гарантирует стабильный `latency` при опросе сетевых устройств 24/7.
  2. **Отсутствие GIL (Global Interpreter Lock)**: В отличие от Python, Rust использует нативные потоки ОС и асинхронность, выжимая 100% из всех ядер CPU.
  3. **Родная интеграция с Wasmtime**: Движок Wasmtime разрабатывается на Rust, что дает безупречный, безопасный и самый быстрый FFI-слой без накладных расходов.
  4. **Совместимость с Tauri**: Tauri написан на Rust, что позволяет использовать единый бэкенд для сервера и десктопа.

* **Почему отвергнуты альтернативы**:
  * ❌ **Python (Текущий стек)**: Наличие GIL, высокое потребление памяти (~300 МБ в простое против ~35 МБ у Rust), отсутствие изоляции плагинов (любой `sys.exit()` или зацикливание плагина кладет весь сервер).
  * ❌ **Go**: Имеет Garbage Collector (GC), который создает непредсказуемые паузы при высоконагруженном сетевом мониторинге. Слабая интеграция с Tauri и более громоздкий FFI при работе с Wasmtime.
  * ❌ **C++**: Высокий риск ошибок безопасности памяти (Use-After-Free, Buffer Overflow, Segfaults), сложная система сборки зависимостей (CMake/Conan).

---

### 2.2. WASM Рантайм: **Wasmtime + WASI v2 (Component Model)**

* **Почему выбран Wasmtime**:
  1. **Официальный стандарт Bytecode Alliance**: Разрабатывается лидерами индустрии (Mozilla, Fastly, Red Hat, Intel).
  2. **Эталонная поддержка WASI v2 и Component Model**: Wasmtime — единственный рантайм с полноценной и самой зрелой поддержкой спецификации WASM Component Model (`.wit`), что позволяет генерировать строгие типы FFI для любых языков (Rust, Go, C++, Zig).
  3. **Поддержка WASI Sockets**: Стандарт WASI 0.2 дает возможность WASM-модулям безопасно выполнять сокетные вызовы для сетевого мониторинга.
  4. **Безопасный Trap-handling**: В случае сбоя в WASM-модуле Wasmtime мгновенно изолирует ошибку и возвращает Rust `Result::Err`, не обрушивая процесс.

* **Почему отвергнуты альтернативы**:
  * ❌ **Wasmer**: Медленнее внедряет стандарты Component Model и WASI v2, сместился в сторону коммерческой экосистемы, имеет менее стабильные Rust-биндинги.
  * ❌ **WasmEdge**: Оптимизирован преимущественно под Edge/AI задачи и специфичные среды Linux, хуже документирован для работы с классическими серверными FFI в Rust.

---

### 2.3. Desktop Framework: **Tauri v2**

* **Почему выбран Tauri v2**:
  1. **Минимальное потребление памяти**: Десктопное приложение занимает ~40-60 МБ RAM (использует системный WebView), в отличие от Electron.
  2. **Компактный размер дистрибутива**: Исполняемый файл занимает ~15-20 МБ (против 120+ МБ у Electron).
  3. **Прямое взаимодействие с Rust-ядром**: Бэкенд Tauri — это тот же Rust-код нашего сервера.

* **Почему отвергнуты альтернативы**:
  * ❌ **Electron**: Поставляет внутри себя полный браузер Chromium и Node.js. Потребляет 300-500+ МБ RAM даже при отсутствии активных действий.
  * ❌ **Flutter Desktop**: Специфический язык Dart, сложности с динамической загрузкой Web Components плагинов, избыточный слой абстракции UI.

---

### 2.4. HTTP Framework & Async Runtime: **Axum + Tokio**

* **Почему выбрана связка Axum + Tokio**:
  1. **Единая экосистема**: Axum разрабатывается командой Tokio и является стандартом де-факто для высоконагруженных веб-сервисов на Rust.
  2. **Производительность**: Обрабатывает сотни тысяч запросов в секунду с минимальным накладными расходами (на базе `hyper`).
  3. **Удобство API**: Элегантная система макросов и экстракторов, аналогичная FastAPI, но со строгой типизацией на этапе компиляции.

* **Почему отвергнуты альтернативы**:
  * ❌ **Actix-web**: Использовал собственную экосистему акторов (раньше), менее прозрачная интеграция с Tokio, чуть более сложен в поддержке.
  * ❌ **Rocket**: Исторически отставал по поддержке async и современной экосистемы Tokio.

---

### 2.5. Frontend & Microfrontends: **Vue 3 + Web Components (Custom Elements)**

* **Почему выбрана эта связка**:
  1. **100% Совместимость с кодовой базой NMS**: Текущий интерфейс `nms-webui` написан на Vue 3. Использование Vue 3 исключает необходимость затратного и рискованного переписывания всего UI на другой фреймворк.
  2. **Нативная поддержка Web Components в Vue 3**: Функция `defineCustomElement()` во Vue 3 позволяет компилировать компоненты плагинов в стандартные Web Components (`ui.js`).
  3. **Изоляция UI стилей (Shadow DOM)**: Web Components гарантируют, что CSS-стили плагина никогда не сломают верстку основного приложения.
  4. **Отказ от Runtime SFC-компиляторов**: Компиляция UI происходит у разработчика на этапе сборки плагина. Браузер получает готовый, минифицированный JS без необходимости запускать тяжелый компилятор в браузере.

* **Почему отвергнуты альтернативы**:
  * ❌ **React**: Потребовал бы полного переписывания существующего фронтенда NMS с нуля, имеет более громоздкую интеграцию с Custom Elements и Shadow DOM.
  * ❌ **Runtime SFC (Vue/React компиляция в браузере)**: Медленная загрузка (задержка 200-500 мс на парсинг в браузере), требует опасного `eval()` / `new Function()`, утяжеляет бандл ядра.
  * ❌ **IFrame**: Ужасный User Experience (сложности с адаптивностью, контекстными меню, модальными окнами и передачей событий).

---

### 2.6. База Данных: **SQLx (SQLite / PostgreSQL)**

* **Почему выбран SQLx**:
  1. **Compile-time SQL Validation**: SQLx проверяет валидность всех SQL-запросов ядра к БД прямо на этапе компиляции Rust-кода!
  2. **Асинхронность**: Нативно асинхронный драйвер для Tokio.
  3. **Поддержка SQLite и Postgres**: Позволяет использовать SQLite для автономного десктопа и PostgreSQL для серверного Enterprise-деплоя с минимальными изменениями кода.

* **Почему отвергнуты альтернативы**:
  * ❌ **Diesel**: Синхронный ORM (требует спавна отдельных потоков для асинхронности), тяжелый DSL, усложняющий простые запросы.

---

### 2.7. Сбор системных журналов и Логов: **Кроссплатформенный Tracing + Multi-OS Log Providers**

* **Почему выбрана эта связка**:
  1. **Кроссплатформенность и абсолютная портативность**: Приложение может запускаться на любой ОС (Linux с systemd/OpenRC, Windows Server, macOS, Docker). Абстракция `LogProvider` на Rust адаптирует чтение логов под текущую систему:
     - **Linux (systemd)**: Нативная интеграция через сокет `systemd-journal`.
     - **Linux (без systemd) / Unix**: Чтение Syslog (UDP/Unix socket) и файлов журналов.
     - **Windows**: Интеграция с Windows Event Log (`winlog`) и файлами логов.
  2. **Единый асинхронный пайплайн трассировки**: Библиотека `tracing` обеспечивает микросекундное логирование событий ядра и WASM-модулей независимо от платформы.

---

### 2.8. Безопасность и Аутентификация: **Argon2id + Ed25519 JWT + Ring**

* **Почему выбрана эта связка**:
  1. **Защита от перебора паролей**: Использование стандарта OWASP Argon2id для хэширования паролей пользователей.
  2. **Быстродействующая криптография**: Пакеты `ring` / `ed25519-dalek` выполняют криптографические операции проверки токенов и шифрования секретов в десятки раз быстрее Python `cryptography/passlib`.

---

### 2.9. Уведомления и Фоновые Задачи: **Tokio Cron Engine + Reqwest Async**

* **Почему выбрана эта связка**:
  1. **Нативная асинхронная рассылка**: Рассылка алеротов в Telegram, Webhooks и E-mail выполняется параллельно без блокировки цикла опроса сетевых устройств.
  2. **Планировщик задач**: Замена тяжелого Python APScheduler на легкий асинхронный планировщик на базе `tokio-cron-scheduler`.
