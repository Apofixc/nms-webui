# Архитектурное руководство и план миграции NMS на Rust + WASM + Tauri

Данный документ представляет собой подробную спецификацию целевого приложения **NMS Next-Gen**, исчерпывающий разбор и обоснование стека технологий (с аргументацией выбора и анализом альтернатив), а также детальный план миграции.

---

## 🏛️ Часть 1. Как работает новое приложение

### 1.1. Двойной режим работы (Dual-Mode Execution)
Новое приложение представляет собой **один бинарный файл**, который адаптирует свое поведение в зависимости от окружения и аргументов командной строки:

```
                                  ┌──────────────────────────┐
                                  │   Исполняемый файл nms   │
                                  └─────────────┬────────────┘
                                                │
                       ┌────────────────────────┴────────────────────────┐
                       ▼                                                 ▼
        [Запуск с аргументом --server]                    [Запуск без аргументов / GUI]
                       │                                                 │
      ┌────────────────┴────────────────┐               ┌────────────────┴────────────────┐
      │ Headless Daemon / Docker        │               │ Tauri Desktop App               │
      │ • Без графического окна         │               │ • Инициализирует WebView окно   │
      │ • Запускает Axum HTTP/WS 24/7   │               │ • Поднимает локальный бэкенд    │
      │ • Выполняет опрос сетей по cron │               │ • Рендерит React UI в окне      │
      └─────────────────────────────────┘               └─────────────────────────────────┘
```

---

### 1.2. Жизненный цикл ядра и WASM-модулей
1. **Инициализация Ядра (Rust Core)**:
   * Запускается асинхронный рантайм `tokio`.
   * Подключается пул соединений БД (`sqlx` с поддержкой SQLite / Postgres).
   * Инициализируется асинхронная шина событий (`tokio::sync::broadcast`).
   * Поднимается рантайм `Wasmtime` с включенными флагами `async_support` и `component_model`.

2. **Загрузка и Изоляция Модулей**:
   * Сканируются каталоги `/modules/*.wasm`.
   * Для каждого файла `Wasmtime` производит валидацию и компилирует его в нативный код текущей архитектуры (AOT/JIT).
   * Модулю выделяется **изолированная песочница** с жесткими лимитами (например, не более 128 МБ RAM).
   * При падении плагина (Trap / Out of Memory) ядро перехватывает исключение, регистрирует ошибку в системном логе и перезапускает плагин **без остановки основного сервера**.

3. **Связывание (Linking) и Маршрутизация**:
   * Модули регистрируют свои обработчики событий в Шине Событий.
   * Если модуль содержит UI, бэкенд отдает файл `ui.js` из байтов `.wasm` через HTTP-эндпоинт `/api/v1/modules/{id}/ui.js`.

## 🔬 Часть 2. Обоснование Стека Технологий (Technology Rationale & Alternatives)

 Ниже приведен детальный анализ выбора каждого элемента стека с аргументацией, почему были отвергнуты альтернативные варианты.

---

### 2.1. Язык Ядра: **Rust**

* **Почему выбран Rust**:
  1. **Безопасность памяти без GC (Garbage Collector)**: Отсутствие пауз сборщика мусора гарантирует стабильный `latency` при опросе сетевых устройств 24/7.
  2. **Отсутствие GIL (Global Interpreter Lock)**: В отличие от Python, Rust использует нативные потоки ОС и асинхронность, выжимая 100% из всех ядер CPU.
  3. **Родная интеграция с Wasmtime**: Движок Wasmtime разрабатывается на Rust, что дает безупречный, безопасный и самый быстрый FFI-слой без накладных расходов.
  4. **Совместимость с Tauri**: Tauri написан на Rust, что позволяет использовать единый бэкенд для сервера и десктопа.

* **Почему отвергнуты альтернативы**:
  * ❌ **Python (Текущий стек)**: Наличие GIL, высокое потребление памяти (~300 МБ в простое против ~35 МБ у Rust), отсутствие изоляции плагинов (любой `sys.exit()` или зацикливание плагина кладет весь сервер).
  * ❌ **Go**: Имеет Garbage Collector (GC), который создает непредсказуемые паузы при высоконагруженном сетевом мониторинге. Слабая интеграция с Tauri и более громоздкий FFI при работе с Wasmtime.
  * ❌ **C++**: Высокий риск ошибок безопасности памяти (Use-After-Free, Buffer Overflow, Segfaults), сложная система сборки зависимостей (CMake/Conan).

---

### 2.2. WASM Рантайм: **Wasmtime**

* **Почему выбран Wasmtime**:
  1. **Официальный стандарт Bytecode Alliance**: Разрабатывается лидерами индустрии (Mozilla, Fastly, Red Hat, Intel).
  2. **Эталонная поддержка WASI v2 и Component Model**: Wasmtime — единственный рантайм с полноценной и самой зрелой поддержкой спецификации WASM Component Model (`.wit`).
  3. **Безопасный Trap-handling**: В случае сбоя в WASM-модуле Wasmtime мгновенно изолирует ошибку и возвращает Rust `Result::Err`, не обрушивая процесс.

* **Почему отвергнуты альтернативы**:
  * ❌ **Wasmer**: Медленнее внедряет стандарты Component Model и WASI v2, сместился в сторону коммерческой экосистемы, имеет менее стабильные Rust-биндинги.
  * ❌ **WasmEdge**: Оптимизирован преимущественно под Edge/AI задачи и специфичные среды Linux, хуже документирован для работы с классическими серверными FFI в Rust.

---

### 2.3. Desktop Framework: **Tauri v2**

* **Почему выбран Tauri v2**:
  1. **Минимальное потребление памяти**: Десктопное приложение занимает ~40-60 МБ RAM (использует системный WebView), в отличие от Electron.
  2. **Компактный размер дистрибутива**: Исполняемый файл занимает ~15-20 МБ (против 120+ МБ у Electron).
  3. **Прямое взаимодействие с Rust-ядром**: Бэкенд Tauri — это тот же Rust-код нашего сервера.

* **Почему отвергнуты альтернативы**:
  * ❌ **Electron**: Поставляет внутри себя полный браузер Chromium и Node.js. Потребляет 300-500+ МБ RAM даже при отсутствии активных действий.
  * ❌ **Flutter Desktop**: Специфический язык Dart, сложности с динамической загрузкой Web Components плагинов, избыточный слой абстракции UI.

---

### 2.4. HTTP Framework & Async Runtime: **Axum + Tokio**

* **Почему выбрана связка Axum + Tokio**:
  1. **Единая экосистема**: Axum разрабатывается командой Tokio и является стандартом де-факто для высоконагруженных веб-сервисов на Rust.
  2. **Производительность**: Обрабатывает сотни тысяч запросов в секунду с минимальным накладными расходами (на базе `hyper`).
  3. **Удобство API**: Элегантная система макросов и экстракторов, аналогичная FastAPI, но со строгой типизацией на этапе компиляции.

* **Почему отвергнуты альтернативы**:
  * ❌ **Actix-web**: Использовал собственную экосистему акторов (раньше), менее прозрачная интеграция с Tokio, чуть более сложен в поддержке.
  * ❌ **Rocket**: Исторически отставал по поддержке async и современной экосистемы Tokio.

---

### 2.5. Frontend & Microfrontends: **React + Web Components (Custom Elements)**

* **Почему выбрана эта связка**:
  1. **Изоляция UI стилей**: Web Components с **Shadow DOM** гарантируют, что CSS-стили плагина никогда не сломают верстку основного приложения.
  2. **Фреймворк-независимость**: Авторы плагинов могут верстать UI на Vue, Svelte, Lit или Vanilla JS — на выходе получается один стандартный `<plugin-widget>`, который React рендерит без проблем.
  3. **Отказ от Runtime SFC-компиляторов**: Компиляция UI происходит у разработчика на этапе сборки `.wasm`, браузер получает готовый минифицированный JS.

* **Почему отвергнуты альтернативы**:
  * ❌ **Runtime SFC (Vue/React компиляция в браузере)**: Медленная загрузка (задержка 200-500 мс на парсинг), требует опасного `eval()` / `new Function()` в браузере, утяжеляет ядро.
  * ❌ **IFrame**: Ужасный User Experience (сложности с адаптивностью, контекстными меню, модальными окнами и передачей событий).

---

### 2.6. База Данных: **SQLx (SQLite / PostgreSQL)**

* **Почему выбран SQLx**:
  1. **Compile-time SQL Validation**: SQLx проверяет валидность всех SQL-запросов к БД прямо на этапе компиляции Rust-кода!
  2. **Асинхронность**: Нативно асинхронный драйвер для Tokio.
  3. **Поддержка SQLite и Postgres**: Позволяет использовать SQLite для автономного десктопа и PostgreSQL для серверного Enterprise-деплоя с минимальными изменениями кода.

* **Почему отвергнуты альтернативы**:
  * ❌ **Diesel**: Синхронный ORM (требует спавна отдельных потоков для асинхронности), тяжелый DSL, усложняющий простые запросы.

## 🗺️ Часть 3. Детальный план миграции (Migration Roadmap)

Миграция разбита на **5 последовательных фаз**, гарантирующих непрерывность работы существующей системы.

```
       [Фаза 1: PoC & WIT]            (2 недели)  ──> Валидация WASM рантайма
       [Фаза 2: Tauri GUI Wrapper]    (2 недели)  ──> Быстрый Desktop дистрибутив
       [Фаза 3: Rust Core & Axum]     (4-6 недель)──> Замена Python бэкенда
       [Фаза 4: Wasmtime Integration] (4 недели)  ──> Внедрение движка плагинов
       [Фаза 5: Стабилизация & Docs]  (3 недели)  ──> Готовый продукт
```

---

### 📍 Фаза 1: Проектирование WIT-интерфейсов и PoC (2 недели)
* **Задачи**:
  1. Создать спецификацию `nms-plugin.wit`, описав методы ядра (`host`) и модулей (`module`).
  2. Поднять минимальный Rust-проект с `wasmtime` и проверить трассировку ошибок (Trap-handling).
  3. Собрать тестовые плагины на **Rust** (`wasm32-wasip2`) и **Python** (`componentize-py`).
* **Результат**: Работающий PoC, подтверждающий корректность FFI-слоя.

### 📍 Фаза 2: Tauri v2 Обертка (2 недели)
* **Задачи**:
  1. Добавить конфигурацию `src-tauri` к существующему Vite React фронтенду.
  2. Настроить запуск текущего Python бэкенда как временно встроенного процесса (sidecar).
  3. Собрать десктопные бинарники `.exe` и `AppImage`.
* **Результат**: Работающая десктопная версия приложения (на текущем Python бэкенде).

### 📍 Фаза 3: Перенос Ядра на Rust (`nms-core`) (4–6 недель)
* **Задачи**:
  1. Написать CLI-парсер (`clap`) с поддержкой режимов `--server` и `--gui`.
  2. Переписать REST API и WebSocket хэндлеры с FastAPI на **Axum**.
  3. Реализовать работу с БД через **SQLx** (SQLite / Postgres) и асинхронную шину событий (`tokio::sync::broadcast`).
  4. Перенести асинхронный планировщик задач (`tokio-cron-scheduler`).
* **Результат**: Полноценный высокопроизводительный бэкенд на Rust, заменяющий Python.

### 📍 Фаза 4: Движок WASM-плагинов и Web Components (4 недели)
* **Задачи**:
  1. Внедрить сканирование и автозагрузку файлов `modules/*.wasm` в `nms-core`.
  2. Реализовать выдачу забандленных JS/CSS ресурсов из `.wasm` по HTTP эндпоинтам.
  3. Обновить React UI для динамического рендеринга тегов `<plugin-widget>`.
  4. Создать базовые шаблоны репозиториев плагинов (`nms-plugin-template-rust`, `nms-plugin-template-cpp`).
* **Результат**: Полнофункциональный рантайм плагинов `.wasm` с поддержкой UI.

### 📍 Фаза 5: Миграция стандартных модулей и релиз (3 недели)
* **Задачи**:
  1. Переписать встроенные модули NMS (Ping Collector, SNMP Scanner, Notification Dispatcher) в WASM-компоненты.
  2. Провести нагрузочные тесты (опрос 10 000+ устройств).
  3. Подготовить финальную документацию для разработчиков плагинов.
* **Результат**: Готовая к продакшну система **NMS Next-Gen**.
